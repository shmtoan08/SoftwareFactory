# T1 stage B2 — authenticated delivery and committed-candidate reconciliation

2026-11-19. Scoped task contract under issue #23 owner approval 6952955719 and instruction to continue after B1. [B1 review210750216](https://github.com/shmtoan08/SoftwareFactory/commit/17b540273244b98d677d65f04e8d34925a42979d#commitcomment-210750216) is ĐẠT with no blocking findings. This slice adds database/telemetry-delivery.ts, a separate connection runner beside the existing private wire client, migration0023 observer staging and a real-PG integration fixture. Legacy pool transaction methods, business interfaces, shared types, provider behavior and runtime composition remain unchanged.

PostgresTelemetryDelivery accepts a dedicated service connection configuration and fixed project. The optional B1 deliver callback can be explicitly connected to this instance, but no runtime constructor does so. Every batch opens its own authenticated connection, SET LOCAL ROLE telemetry_ingestor, and calls assert_ingestor against session_user/registry authority. It never borrows app_runtime connections or joins the business AsyncLocalStorage transaction. No service login/credential/registry binding is provisioned by migration. Remote connections require verify-full TLS; existing TLS CA/server-name validation is reused. Explicit insecure remote/cleartext-auth overrides are refused. Loopback fixtures use existing local authentication settings.

Batches are prevalidated in full (1–100 events); exact fields, UUID/project, literals, bounded identifiers, HMAC shape and canonical numeric strings are checked without invoking getters. Unknown/raw fields are rejected before SQL. Only fixed parameterized statements invoke register_call, append_unverified_usage or stage_ledger_candidate. Provider-specific usage key checks remain enforced in SQL against the immutable invocation. One batch is one transaction; failure rolls back the whole batch. A single instance permits one delivery or reconciliation at a time. The runner has a 2-second operation deadline, <=500ms TCP-connect budget, 2-second statement timeout, 50ms lock timeout and <=1MiB receive buffer. Abort destroys the dedicated connection; cleanup may take an additional bounded wire close interval. Abort during authentication is observed at connection completion/deadline rather than by exposing an unfinished socket. Errors become static messages without SQL, credentials, raw PG details or causes. Lost COMMIT acknowledgement is an uncertain result; stable IDs make event replay safe, never a reason to retry the provider.

Migration0023 adds **ledger_candidates** as append-only observer staging, not a dispatch journal or authoritative in-flight inventory. It records explicit invocation/ledger IDs and a server digest; unique project/invocation/ledger prevents duplicate receipts. It deliberately has no ledger FK because the business row may be uncommitted or rolled back. FORCE RLS, scoped invocation FK, immutable trigger and function-only access apply. No new execution admission, ownership or generation mechanism is introduced.

assert_ingestor additionally rejects any role membership (including NOINHERIT/SET ROLE paths) with ledger INSERT/UPDATE/DELETE/TRUNCATE authority. Thus a configured service cannot create an uncommitted business ledger in its own transaction and pass it off as independently committed evidence. An administrative superuser is already rejected by existing registry authorization; administrators remain trusted DDL authorities.

reconcile_candidates reads a bounded project page (default25,max100) in a separate service transaction. A missing/not-yet-visible/foreign ledger returns pending **without a mismatch marker**. This avoids falsely quarantining a valid TX2 still in progress. Only an independently committed visible ledger proceeds to existing A5 identity validation and settlement; retry returns duplicate and conflicts keep their markers. Commit visibility is tested, not a claim about disaster recovery/fsync configuration. Rollback leaves a pending candidate; this slice does not infer that a permanently absent row is terminal or complete.

Pagination uses a project/candidate UUID key. It is a live bounded diagnostic/reconciliation pass, not a frozen report: newly inserted IDs may precede a cursor, so a future background scheduler must repeat passes from the beginning and account for cutoffs. There is no automatic reconciliation loop, retention/deletion, terminal censoring or independent coverage inventory yet. Candidate events lost before persistence remain unknowable from this table alone. Task attribution/canonical eligibility remain disabled; A5's prompt-ID/version equality still does not verify HMAC against the ledger template.

The real PostgreSQL test connects with an actual dedicated LOGIN and exercises B1-produced sanitized events through the wire transport, including duplicate batch replay. A separate admin writer holds a ledger uncommitted: reconciliation returns pending, rollback still yields no settlement, and a subsequent commit permits recorded then duplicate. Tests cover complete batch rollback on SQL validation failure, unknown fields/getters, foreign project/registry authority, superuser/app_runtime/misprovisioned writer memberships, direct table denial, byte/counter validation through A4, pre-abort, missing database, bounded locked-table failure, no overlapping operations, candidate immutability and revocation. All test data/roles live in a disposable clone and are removed. PG16/17 CI applies0023 twice before the full suite, which includes this integration test.

B1's default1s delivery deadline may abort this transport before its2s maximum; no deadline is silently extended. No production observer, provider/model call, T2 spending or T1/S0-B acceptance is activated.
