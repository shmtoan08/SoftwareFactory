# T1 stage A4 — unverified usage observations

2026-11-18. Scoped task contract under issue #23 owner approval 6952955719: observations/quality storage, a narrowly typed sanitized append function, negative and concurrent-delivery tests. A3 review [210570061](https://github.com/shmtoan08/SoftwareFactory/commit/33fde8c4d849690f6637b2a9115af44a18e6fef8#commitcomment-210570061) accepted the previous slice. Its documentation spacing notes are fixed; approval/digest/transition-order checks remain mandatory before any lifecycle writer is opened.

Migration 0020 adds immutable, project-scoped observations and quality events under FORCE RLS and the existing session_user/service registry authority. Only telemetry_ingestor may execute append_unverified_usage; no service/worker gets table grants. The function derives the candidate schema from the immutable invocation provider. It accepts only project/invocation, kind USAGE/PARTIAL/FAILURE, positive revision, sanitized numeric JSON and an optional reviewed error enum. It cannot accept canonical eligibility, arbitrary mapping/pricing versions, a digest, creation time or lifecycle authority. Unknown/missing invocation and invalid input produce static bounded errors. A FAILURE requires an error category.

The Anthropic and Google key sets are the **candidate parser allowlists already proposed in T0**, not verified current provider contracts. OpenAI has no candidate counter schema here and accepts only the empty object. Every mapping remains unverified. Numeric JSON values must be canonical nonnegative decimal strings of at most 30 digits; JSON numbers, null values, fractions, signs, leading zeros, unknown keys, nesting and oversize payloads are rejected. Missing keys remain missing. The payload limit is 8 KiB; the fixed, bounded remaining fields keep the event under 16 KiB. Raw provider responses, errors and prompts must never be passed to this private persistence interface. Transport/SQL logging configuration and the pre-persistence sanitizer still belong to the future service boundary, not this database fixture.

All observations have canonical_status unavailable, missing_reason mapping-unverified and reasoning_inclusion unverified. Canonical/cache/reasoning counters, billed amount/currency, price version and calculated cost must remain null. Only Google candidate totalTokenCount is copied separately into reported_total; it is never a canonical total, invoice or cost. Provider counters stay in numeric_usage without inferred accounting relationships. The counter domain uses unconstrained NUMERIC with explicit finite/nonnegative/<10^30/integer-scale checks: NUMERIC(30,0) would round fractions before a CHECK. Future readers must serialize numeric columns as decimal strings.

The idempotency key is (project, invocation, kind, revision). Digest generation is server-side over validated content, including the candidate mapping revision. Equal retries return the same observation ID and duplicate; initial insert returns recorded. Conflicting content returns conflict, preserves the original receipt and appends a normalized quality marker. Repeated delivery of the same conflict is deduplicated by a partial unique index; non-conflict health events are not collapsed by that index. The caller **must commit** to retain the marker; the function does not raise after writing it. Rollback/crash/lost markers must still be detected by independent inventory reconciliation later. No report reader or eligibility reconciler is introduced, and unverified receipts are never baseline eligible even before a conflict. Ordinary READ COMMITTED delivery is tested; serialization failures remain observation-delivery failures, not reasons to retry provider calls.

Validation uses real PostgreSQL: authorized/foreign/revoked roles, GUC ignored (authority derives only from the service registry), reader/worker denial, direct table denial, scoped FKs, immutable updates/deletes/truncation, duplicate/conflict behavior, exact integers above JS safe range and at the 30-digit bound, fractional/overflow/non-finite rejection, provider key isolation and privacy canaries. A separate two-connection test holds the first receipt uncommitted, confirms the second is blocked on a PostgreSQL lock, commits the first and verifies duplicate/conflict results plus the durable marker. That test clones only the disposable migrated test database, then removes its clone and unique test role; it makes no provider call. CI runs migration 0020 twice, SQL tests and the concurrent test on PG16/17 before full regression.

No runtime hook, service login provisioning, queue, mapping verification, provider call, observation reader/report, settlement link, lifecycle enrollment/closure or retention job is activated. Lock/delivery budgets and failure isolation on the execution path remain stage B work; the database API is not yet wired into execution. Remaining stage A includes settlement/report storage and typed services; lifecycle authority, amendment/transition protocol and independent coverage remain locked. T1, S0-B and T2 are not complete or activated.
