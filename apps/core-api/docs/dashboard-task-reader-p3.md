## Implemented read contract

`GET /api/v1/projects/:projectId/sessions/:sessionId/tasks` authenticates the existing signed project token and four read roles, validates canonical UUIDs/query values, then independently checks live membership, project and session ownership inside one REPEATABLE READ READ ONLY transaction. A foreign/missing session returns the same 404 after project authorization; a foreign project or stale membership returns 403. Only after that chain does the DAO read tasks, constrained by both tasks.project_id and an EXISTS task_plan_links predicate for the same project/session/task. Existing project task lists and all command/recovery paths are unchanged.

The response uses the exact P0 allowlist: task/project/session IDs, title, literal sourceStatus, validated attempt/rework counters, exact decimal-string activeLeaseEpoch, planned assignee profile ID, recorded lease owner/expiry and source created/updated times. The active lease join checks ID/project/task/epoch; a nonnull broken reference fails 500 instead of hiding corruption as null. Expired lease timestamps remain stored source observations; reading neither refreshes nor expires anything. Multiple distinct planned profiles fail 500. Null assignee or no active lease remain null; planned profile is not principal/worker identity. No contract JSON, source paths, prompts, profile snapshots or worker credentials are exposed.

Default/max page limits are 25/100, strict canonical integers; unknown/duplicate query keys, any `stage`, invalid/duplicate/CSV/case-normalized status or malformed cursor return 400. Repeated `status` accepts each of the 11 exact TaskStatus literals at most once, sorted into a canonical filter set. Absence means all statuses. Per approved D-02, stage remains unsupported in v1; no task stage is inferred from the pipeline session's stage. This slice does not claim the deferred stage feature is complete.

Keyset order is `(updated_at DESC, task_id DESC)` and the predicate compares the complete tuple. SQL preserves timestamp microseconds and UUID order; memory uses normalized six-digit UTC timestamps and canonical UUIDs. Cursor is bounded to 2048 bytes, versioned, HMAC-SHA256 with the existing purpose-derived reader key and constant-time signature verification; its task resource kind, project/principal/session, normalized statuses, limit, timestamp/ID anchor and 15-minute expiry are validated. Invalid signatures/schema/encoding return 400; valid but wrong context/expired cursor returns 409 after current membership/session checks. Anchor is the last returned item, not the extra probe row. P1 cursors cannot be used as task cursors.

Each page has one database snapshot and server fetchedAt from the first SELECT that established it. Different requests are best-effort traversal of changing data: rows may move above/below an anchor, so no exactly-once traversal or cross-request snapshot guarantee is made. Refresh restarts paging. No total count or offset/all mode exists.

## Read-only and bounds

The new service calls `readTaskProjection`, never legacy task/session getters or handlers. PG reuses the independently scoped P1 read-only transaction helper: app_runtime and existing RLS, no inherited write transaction, autonomous work or callbacks; statement 2 s, lock 250 ms, acquisition 1 s, whole operation 5 s. Four fixed parameterized SELECTs cover membership, project, session and the bounded page. The page SELECT fetches limit+1 task rows before lease/assignee projection; scoped joins/aggregate are one SQL statement, not application N+1 queries. All selected fields/functions are explicit reviewed built-ins; no SELECT-star, lock, UDF, recovery or business mutation.

Memory reads its source maps synchronously, validates scope/assignee/lease, checks the deadline throughout scanning and retains at most limit+1 task candidates. Its scoped association map and source scans still depend on total data size. Returned DTOs contain new scalar-only objects, not references to stored task/link/lease objects. Both backends fail generically on source/query/precision/time/serialization errors. JSON response is capped at 1 MiB without silent truncation or partial success.

## Verification and scale review evidence

`packages/test-harness/src/dashboard-task-reader.test.ts` adds **11 tests: memory 5, PostgreSQL 6**. It is included in mandatory `npm test`; `npm run test:dashboard:tasks` runs it alone. Combined P1/P2/P3 harnesses run sequentially (`--test-concurrency=1`, as in npm test), because P1 deliberately takes a table-wide lock for its lock-timeout negative. Local targeted validation passed **31/31 tests, 6 suites, no skips**, on real PostgreSQL 17 plus memory. Full local regression passed 372/372 tests, 55 suites, no failures or skips; typecheck, lint and secret scan passed. Exact-source PG16/17 CI results are recorded in issue #22 at handoff.

Scale fixture adds **21,000 tasks** to the ordinary eight-task fixture: 10,000 linked to the selected session, 1,000 linked to another session, 10,000 unlinked, with repeated microsecond timestamps and status mix. It runs the actual exported DAO statement under app_runtime/RLS using `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, limit probe 101 and a Ready filter. Local observed execution **152.673 ms**, root Nested Loop, 101 output rows; an earlier run was 155.201 ms. This is an observation on the local PostgreSQL 17 fixture, not a production SLA. Required PG16/17 CI reruns the same scale test and prints its own actual duration. No index/schema change is needed for this tested envelope. The fixture also runs three bounded reads while another connection holds an uncommitted task edit, then checks a stable post-write content snapshot remains unchanged by reading and catalog definitions are identical.

This is a limited scale decision for implementation review: existing keys/session link indexes and timeouts suffice for the measured fixture. Arbitrarily larger multi-project data, different planner statistics/hardware/skew and deep filtered pages are not proven fast; output bounds do not bound scan cost. If a deployment requires an index/view or fails the timeout envelope, stop activation and obtain a separate schema/scale decision under P0; do not add migrations here or weaken timeouts.
